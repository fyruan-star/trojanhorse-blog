# Handoff: The Trojan Horse (trojanhorse.blog)

Updated 2 November 2026, when the repo was reorganised and GitHub took over building the site. This is the working guide for anyone, human or AI, picking the project up. The root `README.md` is the short version for editors. `CLAUDE.md` carries the rules that always apply.

**To start a new Claude Code session**, open Claude Code in the repo folder and say:

> Work on the Trojan Horse blog in this folder. Read CLAUDE.md and docs/HANDOFF.md first, tell me the current state in five lines, then ask what I want to change.

## 1. Snapshot

- Live at https://trojanhorse.blog. HTTPS is enforced and `www` redirects to the apex domain.
- An M&A journal by Francis Ruan, Ryan Chian and Timothy Zhang. Cover tagline: "Hidden Risks Behind Promising Deals".
- 35 HTML pages, four of them redirects. Four Trojan Horse stories (Oura, Thorne, Uber on ezCater, and personalized health), a Prologue timeline of ten years of tech deals with ten deal notes and five background pages, a three-story Palo Alto sub-journal, a Tech Atlas (9 sectors, 159 cards, 89 relationships, a Map and a List view, draft 2K-style ratings, and on the atlas-map branch 159 more pages: a profile for each of 144 companies, standings for each sector, and five team pages), a process essay, and a podcast page with no audio yet.
- The site is fully generated by `build.py` and published by GitHub Actions. On 2 November 2026 the new build was checked against the live site: all 54 published files were byte-identical.

## 4. Set up and daily commands

Editing in the browser needs nothing installed. To work locally you need Python 3 (built on 3.13, standard library only) and git. The `gh` CLI is optional and useful for watching builds.

```bash
git clone https://github.com/fyruan-star/trojanhorse-blog.git && cd trojanhorse-blog
python3 build.py                              # writes the site into _site/
python3 -m http.server -d _site 8731          # preview at http://localhost:8731/
pkill -f "http.server"                        # stop the preview
```

## 5. How the build works

`build.py` puts `content/`, `content/stories/` and `content/atlas/` on the import path, empties `_site/`, copies `assets/` into it, then runs in order: `build_index`, `build_stories_page`, `build_process`, `build_horses`, `build_weekly` for each story in `STORIES`, `build_primers`, `build_deals`, `build_desk`, `build_desk_index`, `build_buyers`, `build_atlas`, `build_katabasis`, `build_podcast`. Page templates (`HEAD`, `FOOT`, `SHEET`, `COVER`, `ROOMS` and others) live in `build.py`. It is deterministic: the line art draws from a fixed random seed, so repeated builds are byte identical.

The workflow runs the same command on GitHub with Python 3.13, uploads `_site/` and publishes it. Pull requests run the build only, so a broken edit shows a red X before it is merged. A failed build never replaces the live site.

Stylesheets: `assets/site.css` is used by every page, `assets/story.css` by deal notes, background pages and the Palo Alto stories, and `assets/atlas.css` with `assets/atlas.js` by the Atlas List. The Atlas Map is drawn in WebGL with PixiJS 8.22.0, loaded from jsDelivr (pinned, with an integrity hash) only when the Map is first opened, together with the built `tech-atlas.json`. Its files: `assets/atlas-map.js` (the Map/List switch, navigation, input, full screen, teams, addresses, minimap), `assets/atlas-map-scene.js` (the WebGL scene: sector horses, logo badges, the spotlight, team highlighting, labels), `assets/atlas-map-art.js` (the horse, badge and shooting-star textures), `assets/atlas-map-card.js` (the player card), `assets/atlas-map-core.js` (camera, flight, wheel and swipe, spotlight, label and layout arithmetic, tested with `node --test`) and `assets/atlas-map.css`. The map sits in a framed window (about 80% of the page wide and 70% of the screen high) with a Full screen button. The horse is `assets/images/atlas-horse.svg`, traced from the homepage horse by `scripts/atlas-horse/` and tinted per sector. `build_atlas` also writes one page per company, sector and team into `_site/atlas/` through `atlas_pages.py`, styled by `assets/atlas-pages.css`. Controls, the card and keyboard targets are HTML over the canvas. Without scripts the page shows the List. Fonts come from Google Fonts (Cormorant Garamond). Colours are tokens at the top of `site.css`: navy `#303D52`, cream `#F7F4EE`, and the deeper blue `#1C2675` used for type on the white story pages.

## 7. Procedures

### 7A. Change words on an existing page

Find the page in section 6 and edit the file, in the browser or locally. In content files change only the text inside the quotation marks and keep the HTML tags. Commit, then confirm the build is green and the page is live (section 11).

### 7B. Add a new Trojan Horse story

1. **Research first.** Read the primary documents (filings, releases) and note every figure with its source. Note what you could not read. Section 9 has the evidence rules.
2. **Create `content/stories/<name>.py`** by copying `uber.py`. Required names:
   - `WEEK`: the display date, for example `"1 November 2026"`.
   - `SLUG`: the page name without `.html`. It must be unique.
   - `KICKER`: `"Trojan Horse of the Week"`.
   - `TITLE`, written with HTML entities (`&amp;`, `&rsquo;`).
   - `AUTHOR` (optional): the writer's name, shown under the title on the story page. Leave it out for no byline.
   - `HOOK`: one sentence with a concrete number or tension.
   - `LOGO`: see step 3.
   - `GO`: `(href, label)`, the closing link on the story page. Each story currently links to the previous one.
   - `SECTIONS`: a list of `(heading, [paragraph, ...])`. Paragraphs are raw HTML. An empty heading renders running prose with a larger first paragraph.
   - `NOTE`: the sourcing note under the story. Say where figures come from, what could not be verified, which numbers are your arithmetic, and which people are invented.
3. **Get the logo.** Take it from the company's own site (view source for the header `<svg>` or an `<img src="...svg">`), or from Wikimedia Commons when the site hides it. Uber's header draws its mark in CSS, so its file came from Commons, where it is tagged public domain and flagged as a trademark. Before use, open the file and confirm it has no `<script>`, no `on...=` handlers, no `<foreignObject>`, no `<image>` and no external `href` or `url(http`. Save it as `assets/images/logos/<name>.svg` and set `LOGO = {"file": "<name>.svg", "w": <viewBox width>, "h": <viewBox height>, "name": "<Company>", "height": <px>}`. Choose `height` so the rendered width lands near 100 to 135 px (Oura 34, Thorne 20, Uber 34). A square mark such as Y Combinator's is built as one path with `fill-rule="evenodd"` so the letter knocks out of the square (height 36). The mark renders as a one-colour mask, silver on the homepage and navy on the story page, so it never needs recolouring. Logos are the companies' trademarks, used only to identify the subject.
4. **Add `"<name>"` to `STORIES`** in `content/home.py`. The homepage features the newest story by `WEEK` and the Articles page sorts by it. Stories sharing a date show the later-added one first.
5. **Preview** the homepage and the story at about 1280px, 900px and 375px. Below 900px the cards stack.
6. **Audit** with the snippet in section 11.
7. **Commit** the story file and the logo, push, and confirm the build and the page.
8. Optionally point the neighbouring story's `GO` at the new one.

### 7C. Reorder, hide or retire a story

`STORIES` controls which story pages are built, and breaks ties between stories with the same date. To reorder the list, change the dates in `WEEK`. Removing a name takes the story off the homepage and also stops publishing its page, because the site is rebuilt from scratch each time. If the URL was ever shared, add a redirect first (see `build_stories_page` for the pattern).

### 7D. Podcast page

`EPISODES` in `content/home.py` is a list of `(title, description, status)`. There is no audio yet. The Spotify mark on the homepage links to `podcast.html`.

### 7E. CSS changes

`assets/site.css` section headers, in file order: TOKENS, COVER, TALE, SPOTIFY, THE BELT, FOOTER, RESPONSIVE, THE PICKER ON THE COVER, SILO HEADER, DEFINITION, PODCAST, FIRST PRINCIPLES, KATABASIS, GROUND FLOOR, THE WHITE PLATE, THE PROCESS RAIL, TROJAN HORSES (older, now unused), THE JOURNAL INDEX, LINE ART, TROJAN HORSES (current). The homepage stories are the `.th*` rules, the logo masks are `.th__logo` and `.plate__logo`, and the white story pages use `.plate`, `.white`, `.wp` and `.ch`. Three stories sit in three columns and four sit two by two (`build_index` adds `th__grid--n<count>`, styled by `.th__grid--n4`). Stories stack at 900px. About 76 of 189 class names in `site.css` are used by no page (section 12), so check built pages before deleting any rule.

### 7F. Deal notes, background pages, Palo Alto stories

Each is a dictionary in its content file with a `slug`, title lines, sections and sources. Prologue entries find their deal note by title through `DEAL_LINKS` in `build.py`. Follow the existing entries for shape.

### 7G. Atlas logos, company facts and teams

- **Logo.** Use an official file only: Simple Icons (CC0), the company's own press or media kit, or a Wikimedia Commons file whose page carries an explicit licence tag. Never draw, trace, recolour or reshape a mark. Check the file as in 7B (no script, handlers, `foreignObject`, `image` or external links), save it as `assets/logos/<id>.svg` and add `"logo": {"file", "kind", "source", "license"}` to the company. Add `"ground": "dark"` for a white mark. Files tagged CC BY-SA need an attribution line, so they were left out.
- **Company facts.** Add `bio` fields only from a page you read, with each field's link under `bio.sources`. Leave a field out rather than guess. A founding year that is a predecessor's (Visa's BankAmericard, for example) was left out on purpose.
- **Headline numbers.** `stats` on a card overrides the numbers the profile pulls from the key figure. The validator checks every value appears in the key figure.
- **Teams.** Add or change a team under `teams`. To move one company, set `team` and `team_reason`. Run the validator: it names any tie that needs settling.

## 9. Editorial standards in full

The rules in `CLAUDE.md` are the short version. The detail behind them:

**Structure.** State the thesis early and plainly. Present the prevailing view fairly and name whose view it is, then give the alternative reading in concrete terms. Each paragraph sets up the next. Make load-bearing assumptions explicit. Use a concrete example for each abstract claim and label hypotheticals. Address the strongest counterargument and say what evidence would decide it. End with the practical implication.

**Evidence hierarchy.** Use the company's own filings first (S-1, 10-K, 10-Q, 8-K), then releases from the company or its counsel, then established financial press, then trade press. Commentary and aggregators may be cited only with attribution to what they report. Read the document yourself. Summaries have been wrong here: one gave a different use-of-proceeds figure from the filing, one claimed a Customs ruling that could not be confirmed, and the owner's own notes made a claim about Waymo that the record narrows. SEC pages are huge and fetch tools truncate near 450,000 characters, so late sections such as the principal and selling stockholders table may be unreachable. Say so when that happens.

**Numbers.** Label your own arithmetic. Give a range when outlets disagree. Never present a figure you did not see in a source.

**Quotes.** At most one direct quote per Trojan Horse story, under about 15 words, attributed and linked. Paraphrase everyone else and link them.

**Privacy.** Do not name private individuals who supplied information for a piece.

**Story register.** See `CLAUDE.md`. The owner rejected two earlier Oura drafts: the first never named the horse, and the second was eleven separate findings that read like a walkthrough of the filing. The accepted version has eight chapters, names the horse early, and follows one idea through the numbers (every dollar in an IPO has a return address).

**Length and openings (owner's rule, 3 November 2026).** Every Trojan Horse story stays under 1,200 words including the source note, aiming for 800 to 1,000, and every paragraph must advance the argument. No more "Picture the morning" openings, invented characters, or dates and times as openers: start from a familiar, concrete observation that raises the business question. The personalized health story was rewritten to this rule because the first version spent too long on its waterfall metaphor and on listing companies. All four stories were brought under the cap on 3 November 2026.

**Older pages.** The process page, the Prologue, the Palo Alto stories and the Atlas use a plainer, argument-first register. The Trojan Horse stories are the one place where humor and analogy are wanted.

## 13. Lessons from the build

- Built HTML is never committed now. Edit `content/` or `assets/`, never `_site/`.
- `git add -A` has swept in another session's work. Stage by name.
- A plain string containing `{NAME}` leaked the braces into a page once. Use f-strings only where a line has a placeholder.
- An unquoted shell heredoc runs anything in backticks as a command. Quote the delimiter (`<<'EOF'`) when the text contains backticks.
- Checks can report false confidence when the string you test for is not literally in the file. Read back the thing itself.
- A long document truncated by a fetch tool looks complete. Check what range you actually read.
- Screenshots lag. Measure.
- The owner reads the live site, so an unpushed change is an invisible one.
